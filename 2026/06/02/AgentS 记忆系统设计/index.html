AgentS的记忆

在做这个项目的时候，我一直在跟AI谈天论地，左右手来回倒腾，希望可以探索出最好的记忆系统设计方式，但是结果是：

设计偏向理想化学术方案，把 RAG、向量检索、仿生遗忘、分布式共识全部堆砌进一套记忆系统，过度设计远大于业务刚需：小体量业务功能冗余浪费成本，大体量业务性能瓶颈全埋在底层存储选型与冗余计算；顶层分层思路可取，但落地细节处处埋技术债，大规模上线后运维、性能、合规三面承压。

仔细想想，确实啊！软件工程的核心就是用 工程化方法可控地生产高质量软件，还是更务实一些吧

以下是我真实去设计的时候的一些摸索结果吧

1. 概述

AgentS 的记忆系统以 OpenViking 为唯一持久化存储，本地 SQLite 不再存储记忆内容。记忆按四层命名空间组织，支持跨会话继承、agent 间迁移、经验积累与负反馈闭环。

核心原则

  • OpenViking 是唯一记忆内容 Store — 所有记忆内容 CRUD 走 OpenViking；语义搜索走 OV 内置 find()
  • SQLite 保留元数据索引 — memory_metadata 表支撑结构化过滤（best-effort 一致性 + 定期 reconciliation）
  • WAL 持久化缓冲 — pending_memories 表作为 crash-safe 缓冲，同步写入，异步推 OV；重启后继续 flush
  • 指数退避重试 — pending → writing → success/failed，失败后 1min/5min/15min/1h 退避
  • 四层命名空间 — session / agent / user / resource，各有独立 URI 和层级子目录检索策略
  • Session 层利用 OV 内置三级结构 — OV Session 的 L0 abstract / L1 overview / L2 messages 已覆盖会话上下文；AgentHub 仅维护 pinned/ 下的业务语义（goal / requirements / decision），不自行维护 summary 压缩
  • ETL 迁移管线 — OV Session Extract → Critique → Write（复用 OV 内置 Session Extract，仅 Critique 阶段自定义）
  • 确定性优先 — 时效性判断用规则校验，LLM 只评通用性和正确性
  • 精准反馈归因 — context builder 记录 cited=true 的记忆，点踩时仅惩罚真正参与推理的记忆
  • Memory Merge — 写入前 OV find 相似度检查；不同类型不同阈值（preference 0.85 / profile 0.90 / experience 0.92 / decision 禁止 merge）
  • 经验评分与淘汰 — score = confidence × (1 + log(usage_count + 1)) × feedback_factor；小数据量（< 100 条）不做归档
  • URI 幂等写入 — 以 memory_id 作为 URI 唯一键，重复 flush 时 overwrite 而非新增
  • Memory Relations — 利用 OV Relations 接口，记录 decision→supports→experience / requirement→derived_from→session 等关系

2. 存储架构

2.1 pending_memories — WAL 持久化缓冲

设计原则：不再使用纯内存 Buffer（崩溃丢失不可接受），改为 pending_memories SQLite 表作为 WAL 缓冲。

问题： OV 写入后索引就绪有毫秒/秒级延迟。如果用户刚确立一个 decision，下一句话就要基于这个决定推进，强同步等待会导致卡顿。同时，纯内存 Buffer 崩溃会丢失未 flush 的记忆。

方案： pending_memories 表（SQLite WAL），同步写入，后台异步推 OV。重启后可继续 flush。

3. 四层命名空间

关于 Session Summary 的决策：

OpenViking Session 本身已有三级结构（L0 abstract / L1 overview / L2 messages），
get_session_context() 会自动组装 overview + recent messages。
因此 AgentHub 不再自行实现 summary 压缩逻辑，仅维护 session/pinned/ 下的业务语义：
goal、requirements、decision。这些 pinned 条目永久保留，不参与压缩。

层级检索策略（ContextStrategy）：

Strategy target_uri 侧重 Session Agent User Resource 适用场景
chat viking://session/{conv_id}/ 90% 5% 5% 0% 继续会话/闲聊
coding viking://agent/{agent_id}/coding/ 30% 30% 10% 30% 代码生成
research viking://resources/{project}/docs/ 20% 10% 5% 65% 调研/学习
review viking://agent/{agent_id}/review/ 25% 40% 5% 30% 代码审查

7.3 经验评分公式（修正版）

关键设计：

  • (1 + log(usage_count + 1)) 确保 usage_count=0 时得分不为零
  • max(0.1, 1 + feedback_score) 确保负反馈后仍大于 0，避免新经验被误杀

7.4 经验淘汰策略

设计说明： Top30%/Bottom70% 在大数据量下合理，但小数据量会导致过度淘汰。
改用：总量 < 100 条时跳过归档；总量 ≥ 100 条时按 score < 0.3 阈值归档。
