AgentS的记忆

在做这个项目的时候，我一直在跟AI谈天论地，左右手来回倒腾，希望可以探索出最好的记忆系统设计方式，但是结果是：

设计偏向理想化学术方案，把 RAG、向量检索、仿生遗忘、分布式共识全部堆砌进一套记忆系统，过度设计远大于业务刚需：小体量业务功能冗余浪费成本，大体量业务性能瓶颈全埋在底层存储选型与冗余计算；顶层分层思路可取，但落地细节处处埋技术债，大规模上线后运维、性能、合规三面承压。

仔细想想，确实啊！软件工程的核心就是用 工程化方法可控地生产高质量软件，还是更务实一些吧

以下是我真实去设计的时候的一些摸索结果吧

1. 概述

AgentS的记忆系统以 OpenViking 为唯一持久化存储，本地 SQLite 不再存储记忆内容。记忆按四层命名空间组织，支持跨会话继承、agent 间迁移、经验积累与负反馈闭环。

核心原则

  • OpenViking 是唯一记忆内容 Store — 所有记忆内容 CRUD 走 OpenViking；语义搜索走 OV 内置 find()
  • SQLite 保留元数据索引 — memory_metadata 表支撑结构化过滤（best-effort 一致性 + 定期 reconciliation）
  • 短时缓冲解耦写入延迟 — 当前会话新产生的记忆先写入内存 Buffer（同步），后台异步推 OV；检索时合并 Buffer + OV 结果
  • 四层命名空间 — session / agent / user / resource，各有独立 URI 和检索策略
  • Session 层分离静态指引与动态消息 — 核心 goal/requirements 固定在顶端，近期消息按时序追加；接近 token 上限时自动压缩早期消息为 summary
  • ETL 迁移管线 — Filter → Transform（LLM 视角重写） → Validate → Write
  • 确定性优先 — 时效性判断用规则校验，LLM 只评通用性和正确性
  • 反馈归因用注入追踪 — context builder 记录实际注入的记忆，点踩时惩罚注入的记忆

不做的事情

不做 原因
内存 FAISS 索引 OV 内置 find() 已有向量索引
Session 层语义搜索 会话上下文是时序的，不是语义的
版本向量 / 共识投票 当前单 agent 单聊为主
TTL 过期扫描 / 遗忘 记忆总量远未到膨胀阈值
ACL 细粒度权限 owner 归属制已覆盖
Rerank 跨层重排 固定比例 + 层内排序足够
动态 token 预算 固定比例可满足当前场景
敏感信息过滤 单聊为开发者自身会话
多租户隔离 当前单租户已经够用，实在没必要

已知限制

限制 说明 缓解措施
SQLite ↔ OV 无真正的两阶段提交 metadata 和 OV 写入可能不一致 best-effort + 定期 reconciliation
固定比例 60/20/10/10 特定场景可能低效 当前以"继续任务"为主；接口预留 weights 参数
负反馈需 context_trace 冷启动无 trace 时无法归因 降级为不惩罚，记录日志
群聊不做经验提取 群聊场景极少 共识手动写入 resource 层
只有降权没有升权 好的记忆无法自动增强 后续可加点赞升权
Agent 层无去重 多 session 可能提取语义重复的经验 OV find() 自然按相似度排序；膨胀到阈值时再加扫描
Buffer 重启丢失 进程重启后短时缓冲中的未持久化记忆丢失 Buffer 优先存当前会话最新几轮，丢失影响小；可加定时 flush

2. 存储架构

2.1 Session Buffer（短时缓冲）

问题： OV 写入后索引就绪有毫秒/秒级延迟。如果用户刚确立一个 decision，下一句话就要基于这个决定推进，强同步等待会导致卡顿。

方案： 进程内存中维护当前会话的短时缓冲。

2.2 memory_metadata 表 (SQLite)

一致性：best-effort 同步 + 每 5 分钟 reconciliation。

层 URI 用途 检索方式 生命周期

8. 单聊 vs 群聊

维度 单聊 群聊
继续历史会话 ✅ parent_conv_id (深度 ≤ 1) ❌
迁移给其他 agent ✅ ETL 管线 ❌

8.1 继续历史会话

回溯深度限制： 最多回溯 1 层。若 A→B→C→D 继承链，创建 D 时只拉 C 的消息。若 C 也有 parent，触发强制 Extract：将 A/B/C 的核心 goal/decision 提取为 experience，挂载到 D 的 Pinned Guidelines，阻断递归追溯。
