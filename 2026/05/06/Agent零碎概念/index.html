另外说一下传输协议的问题吧

传输协议

本地MCP tool

本地MCP tool使用stdio（标准输入输出）进行通信，这是一种进程间管道通信协议：

  • 客户端（如LangChain MCP Adapter）将MCP Server作为子进程启动
  • 客户端 → 子进程：通过stdin发送数据
  • 子进程 → 客户端：通过stdout返回数据
  • 消息格式：每行一个JSON‑RPC 2.0消息

外部MCP tool

外部MCP tool（如GitHub MCP Server）遵守Streamable HTTP协议，之前使用的是HTTP + SSE（Server‑Sent Events），这属于计算机网络知识（后续会在网络和Agent相关笔记中详细说明）。

旧版传输协议：HTTP + SSE（Server‑Sent Events）

  • 客户端发送HTTP POST请求→服务端
  • 服务端通过SSE长连接推送数据→客户端（单向流）

通常包含两个端点：

  • /sse: 用GET方式打开SSE长连接，服务端通过它推送消息
  • /messages: 用POST方式发送客户端到服务端的JSON-RPC消息
举个栗子
  1. 客户端 GET /sse
  2. 服务端保持这个 SSE 连接不关闭
  3. 服务端通过 SSE 发送 endpoint 事件，告知客户端POST地址
  4. 客户端 POST /messages 发送 initialize、tools/call 等 JSON-RPC 消息
  5. 服务端通过该SSE长连接推送消息、通知、进度等给客户端

新版传输协议：Streamable HTTP

新版MCP使用统一的HTTP端点，同时支持：

  • POST：客户端 → 服务端（发送请求）
  • GET+SSE：服务端 → 客户端（响应/流式推送）
  • 支持双向流、会话管理、多客户端、自动重连

通常使用一个端点：/mcp

简单请求示例
  1. 客户端 POST /mcp
    body: `{"jsonrpc":"2.0","id":1,"method":"tools/list"}`
  2. 服务端直接返回：
    `Content-Type: application/json {"jsonrpc":"2.0","id":1,"result":{...}}`
流式请求示例
  1. 客户端 POST /mcp
    body: `{"jsonrpc":"2.0","id":2,"method":"tools/call",...}`
  2. 服务端返回：
    `Content-Type: text/event-stream` `event: message` `data: {"jsonrpc":"2.0","method":"notifications/progress",...}` `event: message` `data: {"jsonrpc":"2.0","id":2,"result":{...}}`
这时 SSE 只是这次 POST 响应的流式返回形式，而不是必须提前建立的一条专用 `/sse` 通道。

二者的比较：原来是专门要先让客户端发送一个GET请求，之后服务端建立一个SSE管道来进行后续的服务端到客户端通信，这中间如果断连了，服务端无法及时感知到。

原来的http+sse更适合长连接情况

无论是本地还是外部，都遵循了JSON-RPC2.0格式，这也是MCP存在的一个必要吧，同意了一切的工具格式

SKILL

书接上回讲到了MCP，接下来我们聊聊SKILL。二者不属于同一层级，更像是上下层关系：

  • SKILL：教会模型具体的任务执行流程和规则
  • MCP：提供工具调用的标准化格式说明
    当任务需要调用工具时，SKILL定义“如何调度任务”，MCP提供“如何调用工具”的具体规范。

渐进式加载（动态加载）

这是SKILL设计的巧妙之处，解决了长prompt上下文溢出的问题：只需要将SKILL的名称和简短描述加载到system prompt中，就能让模型识别并使用该技能，仅在需要时才加载完整的SKILL内容。

第一层：仅加载SKILL元数据

核心关键是description字段，它决定模型是否会触发该技能。

第二层：触发后读取SKILL主体内容

SKILL的正文应该像“控制面板”而非知识库，主要包含：

  • 核心工作流步骤
  • 必须遵守的规则和约束
  • 相关资源导航链接
  • 何时读取指定的reference文档
  • 何时运行指定的脚本

第三层：按需加载references、assets、scripts

典型的SKILL目录结构：

核心逻辑：description负责触发技能，SKILL.md负责调度任务，references/scripts/assets负责提供细节实现

这里不得不感慨Anthropic的前瞻性，虽然MCP和SKILL现在看起来是技术发展的必然趋势，但早期提出并落地确实体现了技术洞察力。

通信方式

方案 A：Agent 和沙箱共享挂载目录

  • 文件通过共享挂载目录在Host和沙箱之间传递
  • 控制命令通过API/JSON-RPC协议传递
  • 适合本地Agent场景，建议将Skill挂载为只读模式以保障安全

方案 B：不共享文件系统，仅通过API传输文件

适合多租户部署场景，但大文件传输效率较低。

方案 C：Skill 存储在Host，仅按需复制到沙箱

方案 D：Skill 完全集成在沙箱镜像中

最优解决方案

Skill不应该长期存放在沙箱中，而应该存储在Host的Skill Library中，由Agent统一管理索引。仅在任务执行时，将当前需要的Skill以只读方式挂载到沙箱。

完整架构设计

架构特点：

  • Host保存完整的Skill库
  • Agent在Host上完成Skill发现和渐进式读取
  • Sandbox仅负责执行当前任务
  • 每次仅挂载一个Skill到沙箱
  • 任务执行完成后自动销毁沙箱

Agent思维范式

React（推理+行动）

React是最著名的Agent思维范式，但它不是前端框架，而是Reason（推理）+Act（行动）的缩写，底层逻辑本质上是一个while循环。

流程图 1. 用户目标 2. Agent判断需要的信息 3. 调用工具 4. 观察工具返回 5. 继续推理 6. 再调用工具或输出答案

LangChain的create_agent函数就是基于React范式实现的。

Plan-and-Execute（计划-执行）

该范式通过先拆解任务、制定计划，再逐步执行来完成复杂任务，还会根据实际情况进行重新规划（Replan）。

流程图 1. 目标 2. 任务拆解 3. 制定步骤计划 4. 逐步执行 5. 汇总结果

Reflection（反思）

反思范式通过自我检查和迭代优化来提高结果质量。

流程图 1. 生成初稿 2. 自我检查 3. 发现问题 4. 修改优化 5. 再次检查

无论使用哪种思维范式，**Human in the Loop（人在回路）**都是至关重要的原则，这也是Harness工程的核心思想。通过人的干预来指导Agent的行为，可以避免Agent自主决策导致的问题。

Single-Agent和Multi-Agent

Single Agent

单Agent模式适合小型任务，优点是实现简单，不需要多Agent通信开销。但缺点也很明显：受限于模型上下文窗口大小，无法处理超大规模的复杂任务，容易出现上下文爆炸问题。

Multi Agent

A2A协议

A2A是Google推出的多Agent通信协议，用于解决多Agent之间的协同和通信问题。

关于Agent通信，有一个经典面试题：Agent如何保证输出格式正确？（例如JSON格式）

常见的解决方案有三种：

1. 强制JSON输出格式

这是目前最稳健的方法。主流大模型API（如OpenAI、DeepSeek、Qwen）都提供了强制JSON输出的参数，开启后模型会被限制生成符合JSON语法的Token。

2. Prompt引导

通过系统提示词明确要求模型返回JSON格式，例如：你是一个数据提取器，请返回标准JSON格式的结果。

3. 结构化输出框架（如Pydantic、TypedDict）

使用Pydantic等结构化输出框架，可以直接将模型输出解析为指定的数据对象，无需手动解析JSON。

多Agent分工问题

多Agent架构可以很好地解决单Agent的上下文限制问题：例如将需要大量上下文的任务（如网页搜索）交给子Agent处理，子Agent仅将最终结果和总结反馈给父Agent，而不需要传递完整的中间过程。

同时，我认为不应该让Agent自主决定创建子Agent，而应该在系统提示词中明确规定哪些任务可以交给子Agent处理，避免出现失控情况。

举个典型的多Agent协作例子：

  1. Leader Agent：负责整体任务规划和决策
  2. Coder Agent：负责编写代码
  3. Tester Agent：负责测试代码
  4. Reviewer Agent：负责代码审查

但在实际场景中，经常会出现所有工作最终还是由LeaderAgent完成的情况，类似大学小组作业中经常出现的分工失衡问题。

Prompt

Prompt是与AI最直接的沟通方式，在对话系统中通常会包含system prompt，并且需要拼接memory.md、skill.md、claude.md等上下文信息。

常见的Prompt工程方法包括：

  • Zero-shot：无示例直接让模型完成任务
  • One-shot：提供一个示例
  • Few-shot：提供多个示例引导模型输出

例如前面提到的JSON格式输出，就可以通过Few-shot示例来引导模型生成符合要求的结果。

Context

Context即模型的上下文记忆，核心重点是三层记忆架构和三层渐进式压缩记忆。

三层记忆架构

  1. 短期记忆：当前对话会话中的上下文
  2. 中期记忆：经过智能压缩的会话记忆
  3. 长期记忆：持久化存储的知识库（如CLAUDE.md）

三层渐进式压缩架构

  1. Layer 1: MicroCompact（微压缩）：无LLM调用，纯规则驱动，极致轻量。
    针对工具输出上下文进行压缩，系统定义了可压缩工具白名单（COMPACTABLE_TOOLS），仅对Bash、Read、Grep、Glob等产生大量标准输出的工具进行压缩；而Edit、Write等涉及核心状态变更的操作，输出会被完整保留，确保后续决策准确性。

  2. Layer 2: Session Memory Compact（会话记忆压缩）：基于已有会话记忆进行替换，零额外推理成本。
    仅完整保留最近5轮左右的完整会话，有明确的触发条件。

  3. Layer 3: Full LLM Compact（完全压缩）：调用LLM生成结构化摘要，精度最高但成本也最高。

当上下文窗口剩余空间低于安全缓冲水位线（Claude Code中设置为AUTOCOMPACT_BUFFER_TOKENS = 13,000）时，系统会自动触发压缩机制。

分级回退策略：

  • 首选快速路径：优先尝试Session Memory Compact，无需额外LLM调用，速度最快成本最低
  • 降级重型路径：如果SM Compact不满足条件，自动回退到Full LLM Compact，不惜成本生成高质量摘要以保障任务继续运行

Harness

Harness（框架）约束的不是AI本身的能力，而是AI的执行边界：

  • 约束工具调用权限（如限制危险的bash命令）
  • 约束AI返回格式（如强制JSON输出）
  • 隔离工作区（如沙箱环境）
  • 记录完整的操作日志，方便审计和回溯

对于需要高安全性的工具，通常需要用户确认后才可以执行，所有的工具调用都可以在沙箱中进行约束。

另外，Harness中的Hook设计非常巧妙，可以灵活扩展各种约束和扩展点，后续可以详细展开讲解。

OpenClaw 和 Hermes

OpenClaw是早期比较知名的开源Agent框架，Hermes则在其基础上做了进一步优化。二者都基于React思维范式，但Hermes加入了Reflection反思机制，实现了自我进化能力。

DeepWiki 介绍 DeepWiki是基于Devin开发的仓库总结工具，Devin是微软推出的首款虚拟软件工程师，功能非常强大：可以启动虚拟机、打开浏览器、完成代码编写、测试和部署，甚至可以录制完整的操作过程并反馈给用户。新用户可以免费体验几天，搭载的是Opus 4.7模型。

多Agent 协作能力

OpenClaw和Hermes都支持多层Agent协作，最多可以创建2-3层的子Agent层级：

  • 父Agent通常使用更强的模型（如Opus 4.7）
  • 子Agent通常使用较弱的模型（如Sonnet 4.6）
  • 子Agent仅将工作总结和结果返回给父Agent，而不会传递完整的中间过程

同时，部分工具对子Agent是不可用的，例如：delegate_task、clarify、memory等。

当父Agent销毁时，所有子Agent也会随之销毁。

记忆管理

OpenClaw的短期记忆存储在内存中，长期记忆存储在memory.md文件中，并使用SQLite进行索引：

  1. 向量化（Embedding）：将MEMORY.md和每日日志切分成小块，通过AI模型转换为向量存入SQLite
  2. 混合检索：结合向量搜索（语义匹配）和关键词搜索（BM25）快速定位相关内容，再喂给AI模型

Hermes在OpenClaw的基础上，会将记忆逐步总结为SKILL，实现更高效的知识复用。

二者都支持插拔式记忆扩展，可以接入Mem0等第三方记忆服务。
